## 2. 两个口径决定（写死在代码里，不许放宽）

### 2.1 权威日历 = `kline_daily_enriched` 自身的交易日集合

`load_trading_calendar()` 只扫 `data_dir/kline_daily_enriched/date=*/` 里**有 parquet 的分区**，取分区名日期为交易日。判据 E4-A1：分区集合 vs `read_parquet('…/date=*/*.parquet')` 的 distinct 日期集合**两边各 2,141 天、互差 0 天**（`only_in_distinct=[]`、`only_in_partitions=[]`），首日 `2018-01-08`、末日 `2026-11-06`。

> 注：brief 写「distinct `trade_date`」，该 parquet 里**没有** `trade_date` 列，日期列名是 `date`（分区键 `date=*`）。口径本身一致，只是列名不同；`probe_e4_independent.py` 首次按 `trade_date` 取列直接报 `ColumnNotFoundError`，已按真实列名 `date` 复算。

**禁止**使用 `backend/app/services/data_integrity.py:393-412` 的 `_trading_calendar()`：它只有近一年真数据 + 「周一到周五」回退，对 2018–2026 会静默给出错误日历（把节假日当交易日、把调休当非交易日）。判据 E4-A7 对包内 3 个文件做静态扫描：`forbidden_hits=[]`、`weekday_literals=[]`。

### 2.2 `week_end` 用 ISO 周 = `(iso_year, iso_week)` 二元组

不是自然周序号，也不是只取 `week` 一位。跨年时 12 月末与次年 1 月初可能同属一个 ISO 周（如 `2019-12-31` 属 **2020-W01**），只用「自然年 + 周号」会把不同年份的两个 W01 拆开/并错，从而漏判或多判一个周末。

反证（E4-A4）：把周键换成最常见的错法「自然年 + ISO 周号」后，**总数同样是 451**（错法不会改变计数，只会换日子），但两集合各有 **3 天**不同：

| 方向 | 日期 | 含义 |
|---|---|---|
| ISO 有、错法无 | `2019-01-04`、`2024-01-05`、`2025-01-03` | 这些是当年 W01 的最后交易日，被错法并进了上一年 |
| 错法有、ISO 无 | `2019-12-31`、`2024-12-31`、`2026-11-06` | 前两个属次年的 W01（不是 12 月末的周末）；`2026-11-06` 是数据末端，实现输出 `null` |

> **只断言计数会漏掉这个错**（451 == 451）。所以本批同时给了「逐日集合差」这条判据，独立复算也逐日比对了集合（见 §4）。

跨年锚点（E4-A4 probe，实现产物直读）：`2018-12-28` ISO `(2018,52)` → `week_end=1` 且 `month_end=1`；`2019-01-02` ISO `(2019,1)` → `week_end=0`；`2019-01-04` ISO `(2019,1)` → `week_end=1`；`2019-12-31` ISO `(2020,1)` → `week_end=0`；`2020-01-03` ISO `(2020,1)` → `week_end=1`。

### 2.3 数据末端输出 `null`，不输出 0

最新交易日 `2026-11-06` 所在月与所在 ISO 周都还没结束，**无法判定**它是不是月末/周末 → 两个列都输出 `null`（不是 0.0，更不是 1.0）。理由：若判成 `month_end=1`，任何 `month_end == 1` 触发的调仓都会在 11-06 调仓——那是错的钱，不是「差不多」。判据 E4-A5 的 `null_dates=["2026-11-06"]`。

## 3. 计数断言（brief 要求的两条）

窗口 = **2019-07-01 … 2026-10-30**（1,779 个交易日，与研究侧评估窗同窗；面板本身 2018-01-08 起 2,141 天）。

这个窗口不是我挑来凑数的：契约 v0.10 §3.1（第 192 行）自己钉死「评估窗 `2019-07-01`…`2026-10-30` 内 1,779 天」，§5.6 `E4-A1` 写「S07 **同区间** `month_end` 个数 88」、`E4-A2` 写「S06 **同区间** `week_end` 个数 376」，§3.4.3 `XS-C1` 又把 88 个月末 / 376 个周末这同一集合用于 `xs_rank_pct` 的历史复现。brief 给的 88 / 376 就是这两个同区间计数，实测能复现。

| 列 | 窗口内计数（断言值） | 全帧计数（参考） |
|---|---|---|
| `month_end` | **88** | 106 |
| `week_end` | **376** | 451 |

- 全帧 106 个月末 = 2018-01 … 2026-10 的完整月份（2026-11 未结束 → `null`，不计）。
- 窗口 88 = 2019-07 … 2026-10 的 88 个完整月份；`week_end` 376 为同窗内 376 个完整 ISO 周。
- 长假周（某 ISO 周只有 1 个交易日）该日仍是该周的 `week_end`，只算 1 天；跨年周按 ISO 二元组归属，不重复计。

## 5. 帧起点必须固定 `2018-01-08`（写进代码与本文）

`calendar_axis.FRAME_START = date(2018, 1, 8)`，`factor_provider.params()` 把 `frame_start` 暴露成诊断参数。

这两个日历列**本身与帧起点无关**（日级，只看日历）。但同一帧上如果还要算 `in_universe`，它的 `observed_bars` 走 `cum_count`（面板内 bar 行数）——**起点一晚就退化成滚动口径**，池子会变小，而代码一行不改、所有验收判据仍然全绿。判据 E4-A6 给出退化演示（评估日 `2026-09-30`，行数同为 3,188）：

| 起点 | `observed_bars` 最大值 | 当日池内家数 | 相对全帧 |
|---|---|---|---|
| **2018-01-08（固定）** | 2,119 | **1,790** | — |
| 只前置 120 根（`warmup_start=2026-04-09`） | 120 | 1,730 | **−3.352%** |

> 这正是「多剔 277,304 标的日 / 1,274 只」那类口径漂移的来源：不是算法错，是起点没写死。所以起点由调用方固定，并在 `calendar_axis.py` docstring、`params()` 与本文三处写明。
