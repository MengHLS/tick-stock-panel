# 文档维护规范

责任：文档管理员维护登记与链接；原作者维护内容和结论；总体规划负责人维护范围、依赖与交付顺序；独立审核工程师给出基于确切版本的审核结论。

1. 交付时提供仓库相对路径、主题、类别、责任人、文档版本、来源、关联实现/测试/报告、真实命令与退出码、局限、替代关系。无文件登记进行中；文件存在只升级为已交文档，不能升级已验收。
2. 类别区分规划草案、研究规格、架构契约提案、实现说明、测试记录、独立审核和历史档案。复合报告保留正文声明及其范围，必要时按子能力登记；研究代码不等于生产实现。
3. 状态分别维护：草案/待确认/进行中/已交文档；实现状态；验证状态；独立审核状态。已实现须定位实际代码及版本，已验证须有对应版本、输入、命令、结果；独立验收须有真实独立审核结论。不得凭文件存在、测试数量或作者自述合并成已验收。
4. 机器登记册为结构化状态来源，分类清单和统一入口同步更新。路径采用仓库相对路径；未提交文件以SHA-256固定，已提交文件另留最后变更提交和时间。核实日期表示核实范围，不能冒充原作者修订日期；mtime不作语义版本。
5. 代码/API/数据/规则/测试变化，或来源报告更正、审核退回、文件移动、责任人变化时立即复核相关条目。摘要变化先降为待复核，旧验证不得无条件沿用；保留旧来源及更正原因。
6. 冲突、重复、断链和可能过期仅登记事实、受影响范围和待核实责任；交原作者确认。主题重叠不等于内容重复，旧日期不等于失效。只有明确替代和适用版本证据才标过期。首轮不移动、删除、重写原文，不覆盖并行修改。
7. 本地链接检查至少覆盖所有新增Markdown目标、登记路径及证据路径，区分缺失预期交付与真正断链。外链、纯锚点、HTML和代码字符串若未检查必须说明。更新后核对差异及限定目录Git状态；不提交、部署、重启或交易。
8. 作者删除或整编文件时，登记项不删除、不改写历史：标 `removed` 并记删除时间与原因，链接改文字说明；自动生成物（如 `runs/<时间戳>/summary.md`、逐次试验的中间 JSON）不逐次登记，按目录/脚本口径记一条说明，避免登记册跟随重跑抖动。

原文规范以 [CONTRIBUTING.md](../../CONTRIBUTING.md) 和 [现有文档维护规则](../README.md) 为准。本目录按用户指定集中存放治理索引；本轮保留原有入口，跨入口回链由其维护者协调追加。

总体规划交接格式：在原独立规划目录交付原文；向文档管理员提供路径、版本/摘要、责任人、状态、证据与限制。管理员登记后回执，规划负责人只在自己的入口引用本目录README，不直接改登记册；实施、验证、审核各自交付后逐阶段补证据。
