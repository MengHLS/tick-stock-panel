### 2.3 失败机理（代码级，逐行）

1. `store.py:189` `_NON_CONTENT_FIELDS = {"version","created_at","updated_at"}` —— **黑名单**判定：除这三个键外"全部字段逐字段等价"。
2. `store.py:207-215` `content_signature()` 把剔除上述三键后的**整个字典**规范化后逐字比对；`store.py:217-219` `is_same_content()` 就是两个签名相等。
3. `api/factors.py:236-242` `CustomFactorCreateRequest` **没有 `lang` 字段**；`api/factors.py:334-352` 构造的 `definition` 字典也**没有 `lang`**（字段仅 id/kind/version/label/group/formula/description/direction/status/created_at/updated_at）。
4. 盘上 8 个定义**都有** `"lang": "dsl"`（现读原文确认，如 `uf_vol60.json`、`uf_ma120.json`）。
5. 于是 `content_signature(盘上)` 含 `"k:lang":"s:dsl"`，`content_signature(API)` 无该键 → **判成"内容变了"** → 走 `upsert_definition` 的 else 分支（`store.py:240-257`）：`base+1` 抬版本 → `register_factor` → `_STORE.save_one()` **原子覆盖写**（`store.py:256`）。
6. 重写用的 `updated` 来自 API 字典，**盘上多出来的键不会回填**，所以 `lang` 被抹掉（实测 8/8 `file_lang=<absent>`）。
7. `to_spec`（`store.py:72`）对缺 `lang` 的定义**默认按 `"dsl"` 处理**，所以两侧 `FactorSpec` 完全相同（T5 `to_spec_equal=True`）——**语义等价，签名不等价**，这正是缺陷所在。

### 2.4 「等价是对称的吗」——明确回答：**判定函数对称，输入域不对称**

- `is_same_content(stored, incoming)` 是同一个函数、同一套黑名单，参数顺序不影响结果 → **函数层面是对称的**，不存在"落盘→API 单向"的代码差异。
- 但**两侧输入的键集本身不相等**：API 构造的字典是"落盘字典的子集（缺 `lang`）"。所以：
  - 落盘→落盘：判等成立（T1）；
  - API→落盘：判等不成立（T2）；
  - 交替：永久乒乓（T3）。
- 结论：**"两种来源互判等价"不成立**，不是单向问题，而是两个方向都错，只是错误的表现形式不同（API 侧被判"变了"，盘上侧被判"变了"）。
