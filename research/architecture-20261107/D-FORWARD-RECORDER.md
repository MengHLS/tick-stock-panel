# D 部分：只记录、不下单的每日信号记录器 —— 可行性与最小契约

状态：**契约设计，不含实现**。按职责边界，实现属于系统开发工程师；本文只定义「必须满足什么才算合格」。未改任何生产源码。

---

## 1. 结论先行

**技术上可行，且是当前唯一能积累真前瞻样本的手段。** 但它有三个前置条件，缺一条记录就没有证据价值：

1. **规则冻结在先**：策略 key、参数、宇宙定义、成本口径、执行假设全部写死并取哈希（`PROTOCOL.md` §5「F1 起点只能是……全部真正冻结后的首个可执行交易日」）。冻结前产出的记录**不计入 F1**。
2. **口径唯一**：`matching=open_t+1`、`entry_price_basis=raw`、`block_limit_open=True`、5 项成本显式传入（B 段已证研究侧如此配置，`common.py:313-332`；生产默认与之不同，`api/backtest.py:95`）。记录器必须用**和回测完全同一份** config 构造器，否则记录与回测不可比。
3. **输入就绪闸门**：当日截面没算全就记「blocked」，不记「零信号」（C 段 §2.1-5）。

为什么值得做：**回测永远证明不了样本外**（`PROTOCOL.md` §5 已承认 T1/T2 都「已烧」，只能靠 F1/L1）。记录器的唯一价值是**在规则不动的前提下，把未来变成可检查的既成事实**。

## 2. 最小契约（五件事，缺一不可）

### 2.1 信号落库结构

**一条记录 = 一次「某策略在某交易日对某标的给出的一个动作」**，append-only，不改写历史。

| 字段组 | 字段 | 说明 / 约束 |
| --- | --- | --- |
| 身份 | `record_id` | 内容哈希，可去重 |
| | `strategy_key` / `strategy_version` | 例：`S08_near_52w_high` / `v2-frozen-20261106` |
| | `signal_date` | 信号日 T（收盘后可知），ISO 日期，**Asia/Shanghai** |
| | `symbol` | 6 位代码（与面板一致） |
| 动作 | `action` | 枚举：`entry_candidate` / `exit_candidate` / `hold` / `no_action` |
| | `score` | 排序键原值（各条不同：ret20 / -vol60 / rsi14 …） |
| | `rank_in_universe` | 当日截面名次与分母（`rank/total`），空值必须显式 null 并给原因 |
| 决策依据 | `inputs` | 该策略真正读到的量（如 `ret20, ma20, ma60, dist_52w_high`…），**逐字段落盘**，不要只存布尔结论 |
| | `universe_pass` / `universe_reject_reason` | 池子判定结果与**拒绝原因**（`bars<120` / `st` / `price<3` / `amount20<1e8` / `volume=0`） |
| 参考价（**不是成交价**） | `ref_close_raw` | T 日原始收盘（`raw_close`） |
| | `ref_next_open_raw` | T+1 开盘原始价；**T+1 之前必须为 null**，不得预先写入 |
| 可执行性（参考） | `executable_hint` | `open_t+1` / `blocked_limit_up_at_open` / `suspended` …，**只作提示，不作成交** |
| 快照指针 | `snapshot_id` | 指向 §2.2 的输入快照记录 |
| 运行归属 | `run_id` | 指向 §2.3 的运行台账（ok/blocked/failed） |

**硬约束**：
- **不写任何持仓、现金、盈亏字段。** 一旦写了，它就变成了一个假账本（§2.5）。
- **不写 paper 账户**（`api/paper.py` 的账户体系与本表物理隔离）。
- 唯一键：`(strategy_key, strategy_version, signal_date, symbol, action)`；同键重复写入必须幂等（同快照 → 忽略；不同快照 → 新 `revision`，**不覆盖**）。

### 2.2 可复现输入快照

每次运行必须留下**能重算出同一结果**的指纹，否则记录只是「有人说过」。

| 必须记录 | 依据 / 现成件 |
| --- | --- |
| 面板内容指纹（对当日参与计算的行取哈希） | 研究侧已有 `common.py:114-115` 的 `fingerprint()`（`sha256(frame.hash_rows(seed=74))`），可直接复用 |
| 数据修订戳（数据被回补/修正时能发现） | `api/backtest.py:568-578` 的 `_daily_data_revisions() / _stamp_daily_data()` 已有同类机制 |
| ST 历史指纹 | `security_status.py:163-173` 已提供 `st_history_fingerprint()` |
| 宇宙定义（阈值常量） | `common.py:64-68`（`min_price_raw=3.0 / min_prior_amount20=1e8 / min_observed_bars=120`） |
| 成本与执行口径 | `common.py:49-61` 的 `ACCOUNT`，须整块落盘 |
| 代码版本 | `git rev-parse HEAD` + **是否有未提交改动**（`git status --porcelain` 非空必须记 `dirty=true`） |
| 运行环境 | Python 版本、polars/numpy 版本（浮点行为差异会导致边界信号翻转） |

**判定规则**：`snapshot_id` 相同 → 结果必须逐行相同；不同且未解释 → 该日记录标 `suspect`。**没有这一条，记录器只是日志。**

### 2.3 失败必须可见（不许静默）

一天至少有四种状态，**必须互斥且落盘**：

| 状态 | 含义 | 必须携带 |
| --- | --- | --- |
| `ok` | 算完，且**确实算出了完整的截面** | 参与只数、候选数（允许为 0） |
| `empty` | 算完但当日无候选 | `candidates=0` + 池子只数（**与 `ok` 区分开**，避免「零候选」被误读成「出错」） |
| `blocked` | 输入未就绪（数据缺分区/截面只数低于阈值/非交易日错判） | 具体原因码 + 期望值与实际值 |
| `failed` | 抛异常 | 异常类型 + traceback 摘要 + 退出码 |

**可见性要求**（三条，缺一不可）：
1. **覆盖率**：当日「应有只数 / 实际算出只数」必须落盘。比例异常（例如 <90%）自动降级为 `blocked`。
2. **缺口表**：连续未记录的交易日在任何时刻都能被列出（不是「看起来没数据」，而是「明确缺失」）。
3. **心跳**：`run_started_at / run_finished_at / duration`，超过 N 小时无记录即视为中断。中断**不得**用「补记」掩盖——补记必须标 `backfilled=true` 且**不计入 F1 天数**。

### 2.4 交易日与时区口径

| 项 | 规定 | 理由 |
| --- | --- | --- |
| 时区 | 全链路 **Asia/Shanghai（UTC+8）**，落盘用带时区时间戳 | 服务器可能是 UTC；跨时区会把「T 日 15:30」记成「T-1 日」，直接破坏时序 |
| 信号产生时点 | T 日 **15:00 收盘后**，且当日日线分区已落盘 | 15:00 前的数据不完整，用它算信号等于偷跑 |
| `signal_date` | = 产生信号的那个交易日 T | 与回测「信号日」严格一致 |
| 可执行日 | = T 的**下一个交易日**开盘（09:30） | 对应 `entry_delay_bars=1`（`engine.py:1384`） |
| 休市处理 | 用 `services/trading_day.py` 判定；T 后若连续休市，可执行日顺延到下一个交易日 | 不能按「自然日 +1」 |
| 月末/周末再平衡 | 用「下一交易日是否跨月/跨周」判定（`common.py:160-170` 的研究口径），记录器必须用**同一判定** | 口径不同 → 记录的再平衡日与回测不同，两者永远对不上 |
| 记录与 F1 计时 | 只有 `snapshot_id` 完整、状态 `ok/empty`、且规则已冻结的日子才计入 F1；`blocked/failed/backfilled` 不计 | 否则「跑起来了」会被误读成「样本在积累」 |

### 2.5 「记录 ≠ 成交」的边界（最重要的一条）

**记录器允许做的事：**
- 记录「按规则今天会给出什么信号」；
- 记录 T+1 开盘价（等它真实出现后**回填**该字段，且标注 `observed_after_the_fact=true`）；
- 记录「若成交，按模型成本口径的名义价」（必须字段名带 `nominal`，**不得**叫 `pnl`）。

**记录器禁止做的事：**
- 写 `api/paper.py` 的账户/委托/成交（那会让「记录」变成「假设已成交的持仓」）；
- 生成任何「已成交」标记；
- 把名义收益累加成策略业绩曲线并对外称「实盘/前瞻业绩」；
- 因前一日记录「看起来赚了」而改参数——一旦发生，F1 立即作废（`PROTOCOL.md` §5-2）。

**边界一句话**：**这张表证明「规则被执行过」，不证明「策略赚钱」。** 想谈赚钱，必须另起一个**事后评估**流程，且必须显式标注「用记录重放的模拟结果，非实际成交」。

## 3. 最小可行落点（不碰生产源码）

按我的职责边界，建议**第一期只做研究侧**：

```
research/strategy-search-20261107/record/          # 新增，独立目录
  record_signals.py        # 每日跑 S01–S12，写 append-only parquet
  ledger.parquet           # 信号台账（§2.1）
  runs/*.jsonl             # 运行台账（§2.3）
  snapshots/<snapshot_id>.json   # 输入快照（§2.2）
```

调度方式二选一（都算合格）：
- 手动/半自动：每天收盘后跑一次，失败就红；
- 挂系统调度：复用 `jobs/daily_pipeline.py:1313-1317` 的 `CronTrigger(day_of_week="mon-fri", hour, minute)` 写法，**但必须排在数据同步之后**。

**为什么先不接生产**：接生产要动策略注册、新表、API、前端，属于 C 段 §2.1 的 6 项改造；而记录器的价值在**从今天起积累**，不在于架构优雅。研究侧 append-only 文件已经能满足 §2 的全部契约。

## 4. 验收（这份记录器算不算合格，用这 6 条判）

1. **可复现**：拿 `snapshot_id` 重跑，逐行一致（含边界信号）。做不到 → 不合格。
2. **可发现**：人为删掉一天的分区数据，运行必须 `blocked` 且原因码明确；不产出半套信号。做不到 → 不合格。
3. **可区分**：`empty` 与 `failed` 在台账里必须不同；不允许用一个 `ok` 吞掉两者。
4. **可追溯**：任何一条记录都能反查到当时的参数、宇宙阈值、成本口径、代码版本与 dirty 标记。
5. **不越界**：全库搜索确认记录器**没有**写 paper 账户、没有生成「成交」字段、没有产出「业绩曲线」。
6. **不回头**：记录期内参数与宇宙定义未发生任何变更（用 `params_sha256` 逐日比对），否则该段记录作废并重新计时。

## 5. 未知 / 待确认（不猜）

1. **12 条规则是否就是最终冻结形态**——`STRATEGIES.md` v2 是冻结的**规格**，但 `PROTOCOL.md` §10 明确「候选规则尚未真正冻结」。**F1 起点因此尚未成立**，现在开始记录也只能算「预演」，除非先做一次正式冻结并登记。
2. **回填 T+1 开盘价的时点**：需要「T+1 数据落盘」的判定标准（分区存在？mtime？数据修订戳？），C 段 §2.1-5 的闸门阈值也同此问题——**均未定**。
3. **截面只数阈值**（覆盖率 <x% 判 blocked）需要 30 天真实运行后才有依据，现在给任何数字都是拍脑袋。
4. **数据修订导致的历史信号变化**：`snapshot_id` 变化时是「新 revision」还是「视为新样本」，涉及试验计数口径，**属研究员决定**，我不代填。
